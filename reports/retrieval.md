# Retrieval and queue-driven processing (Phase 5)

Status: implemented and measured on one machine (Apple M4 Pro, macOS, Metal). Everything below
is reproducible with the commands in §Reproduction. Failures and limits are in §Limitations.

## 1. Architecture
```
record_source ──(1 tx)──▶ Source + extract job ──▶ receipt {source_id, created, processing}
                                   │ (worker, provider; user approves the exact hash)
approve_extraction ─(1 tx)─▶ Claims + claim_access + index_lexical(prio 90) + index_embed(prio 20)
index workers: lease batch ─▶ recompute work from authoritative rows ─▶ (embed outside any tx)
               ─▶ short fenced write tx ─▶ done | cancelled(obsolete) | deferred | pending(backoff) | failed
search: plan ─▶ exact/lexical ─▶ [semantic if useful] ─▶ gated RRF ─▶ [graph] ─▶ [temporal] ─▶ authoritative recheck
```
Reuse of the existing job table (no external queue). Schema v4 adds `index_lexical`/`index_embed`,
`deferred`/`cancelled`, `priority`, `generation`, `detail` and per-stage timestamps.

## 2. Query planning
`retrieval::planner` is a pure function of query text, hints and request shape (no model). Signals:
quoted phrases, identifiers/paths/code symbols, numbers, time cues (EN/KO), relationship cues,
exhaustiveness cues, question form, script mix. Intent ∈ exact, lexical, semantic, relational,
temporal, comprehensive; depth ∈ focused, balanced, exhaustive. Hints are advisory (flagged when
the query does not support them); ambiguity adds complementary paths. The plan (paths, `when`,
budgets, stop rule, fallback, uncertainty) is returned in every response.

## 3. Lexical retrieval
Tokenizer v1: Hangul/Han/kana character bigrams (unigram for one-character runs), whole ASCII
words and identifiers with joiners plus camelCase/letter-digit parts, jamo composition and
full-width folding, case folding only in the index. FTS5 (contentless, detail=none) only
enumerates matches; BM25 is computed in Rust with N, average length and df measured **inside the
caller's projection**. Exact matching (verbatim phrase/identifier after folding) is a separate
tier from fuzzy matching. Index rows are versioned by tokenizer and rebuilt by queue jobs.

## 4. Semantic retrieval and runtime
Local `nvidia/Nemotron-3-Embed-1B` (pinned revision c0c9fea9…, file digests verified at load,
license in the model directory), candle on Metal (f16) or CPU, bidirectional attention, mean pooling,
1024-d Matryoshka slice, mandatory `query: `/`passage: ` prefixes. Parity with the PyTorch f32
reference: cosine ≥ 0.999998 (`examples/embed_check.rs`). Throughput ≈ 52 texts/s on this machine.
Vectors are persisted as f16, keyed by model identity; exact brute-force cosine over an in-memory
f32 copy (multi-threaded). Cloud embedding (OpenRouter) is opt-in; paid models require a separate
budget ledger and nothing falls back to a remote provider. This work made **zero** paid API calls.

## 5. Fusion, graph and temporal
Gates (development split only): lexical coverage ≥ 0.50 with script overlap; cosine ≥ 0.35.
Gated lists are fused with RRF(60); exact first; duplicate texts collapse; per-Source overflow is
demoted. Graph expansion (dependencies, relations, revisions, same-Source, citations) is bounded by
hops/nodes and runs inside the projection and filters; results are marked `related` with the edge.
Temporal: `as_of` and temporal intent evaluate statuses with the Phase 4 history rule; superseded
Claims are kept as history; Claims not yet stated at `as_of` are excluded and reported.

## 6. Queue, status and recovery
Leases are fenced by attempt number; expiry returns work to the queue; exhausted jobs become
`failed` with a fixed diagnostic code; unavailable providers `defer` without consuming attempts;
`retry_job`/`resume_deferred` are owner-only. `queue_status` reports counts per kind/state, backlog
age, retries, wait/processing/end-to-end percentiles, index progress and health. Per-Source stage:
stored_not_extracted → awaiting_approval → published_awaiting_lexical → awaiting_embedding →
fully_indexed (or failed/deferred/stale). Crash recovery is covered by a SIGKILL test.

## 7. Consistency and authorization
`claim_access` is maintained in the transaction that changes lifecycle/validity/confirmation/
publication; retrieval never reads a hidden Claim's score, count or alias. Tests: forgotten/
retracted Claims never returned from stale indexes; identical scores/ranks/counts with and without
hidden records; cursors bound to credential and query; Phase 4 invalidation excludes immediately;
adversarial race test (forget/retract/restore, index rebuilds and workers running concurrently
while searchers assert no forgotten Claim is returned).

## 9. Large-corpus benchmark (100,000 Claims)
Machine: Apple M4 Pro, 12 CPUs, macOS (aarch64), local Nemotron-3-Embed-1B on Metal (f16). Method:
`examples/retrieval_bench.rs` generates 100,000 Claims through plain SQL (ko/en mix, ≈10% near
duplicates, identifier/path tokens, dependencies, 3% forgotten/retracted, 2% agent-recorded),
opens the app (derives access/validity, enqueues index jobs), then drives the real queue workers.
Raw output: `reports/evidence/retrieval-bench-100k.json`.

| peak RSS / database size | 2639 MB / 605 MB |

Notes. Ingestion stays at millisecond latency while indexing runs, because the synchronous path
only stores and enqueues. **Search latency rises under concurrent embedding** (p95 2.7 s vs
299 ms idle): the embedding worker contends for the GPU/CPU and the vector
cache refreshes as vectors arrive; background QoS does not isolate this fully. Embedding wait is
long only because the entire backlog was enqueued at once. The synthetic text has ≈2,000 distinct
sentences, so the benchmark's known-item recall (≈0.05) is not meaningful and is not a quality
claim; quality is measured in §8. Recovery after SIGKILL and duplicate/stale delivery are covered by
`tests/retrieval_queue.rs`, not by this benchmark.


## 10. Limitations (measured, not hidden)
- **No-answer queries still return something.** The semantic gate (cosine ≥ 0.35) does not reject
  topically adjacent Claims: adaptive no-answer false-positive rate is 0.73 on the new set (0.0 on the
  R3 holdout, whose no-answer cases are absent). No hidden/forbidden Claim was returned, but unrelated
  visible Claims are. A calibrated reject threshold needs more labelled negatives.
- **Gated fusion does not beat semantic-only on MRR** here (0.851 vs 0.905 new set; 0.786 vs 0.861 R3
  holdout), because lexical evidence in a cross-language-heavy set mostly adds noise. Adaptive keeps
  lexical for exact identifiers/paths (exact R@5 = 1.0) and avoids semantic calls in 21% of queries.
- Lexical-only is weak across languages by construction and reports `exhaustive=true` when the
  lexical index is complete even though paraphrases are missed (false-completion rate 0.50 for the
  lexical-only diagnostic strategy; adaptive 0.0 because semantic coverage is always "bounded").
- Entity/negation confusion survives at lower ranks (2 forbidden-neighbour hits in 261 judgements).
- Temporal and relational categories have few queries (9 and 3); treat their scores as indicative.
- Bulk families are templated; they test candidate-set pressure and identifiers, not paraphrase.
- Peak memory is dominated by the resident model (several GB incl. Metal buffers) and the f32 vector
  cache (≈4 KB/Claim). First query after start loads the model (~20 s).
- Search latency degrades while the background embedding worker runs (see §9); a stricter isolation (separate process or throttling) is future work.
- Embedding 100k Claims takes about half an hour on this machine; semantic coverage is partial until
  the background worker finishes, and responses say so.
- Cloud embedding was exercised only up to the budget gate (no network calls were made).

## 11. Reproduction
```bash
python3 evaluation/retrieval/generate.py
cargo build --release --example retrieval_eval --example retrieval_bench
target/release/examples/retrieval_eval evaluation/retrieval/dataset.json --out reports/evidence/retrieval-eval-new.json
target/release/examples/retrieval_eval evaluation/retrieval/r3_holdout.json --splits r3_holdout --out reports/evidence/retrieval-eval-r3.json
target/release/examples/retrieval_eval evaluation/retrieval/dataset.json --sweep          # dev-only calibration
target/release/examples/retrieval_bench --claims 100000 --embed 100000 --out reports/evidence/retrieval-bench-100k.json
cargo test --offline --all-targets
```
